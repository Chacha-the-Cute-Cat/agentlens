审查发现问题（5 严重 / 8 高 / 10 中）

整体判断：这是一个架构意识良好、模块边界清晰的安全产品原型。控制面输入验证、设备 DACL、PID+创建时间校验、写时复制策略快照、事件关联 ID 等设计都体现了成熟的 Windows 驱动开发思路。但作为安全产品，当前实现存在一批影响可用性与内核正确性的问题：事件通道在“服务共享环读取”这条主路径上存在崩溃级缺陷，内核侧还有两处并发 / IRQL 正确性问题。README 已声明“不得在生产环境加载未签名构建”，本报告的结论支持这一谨慎态度。

一句话结论：框架与思路值得肯定；事件通道（环形缓冲）、策略 epoch 回收、自旋锁内分页池三处必须修复后才能进入可信度更高的验证阶段。建议继续在隔离 VM 中开发，并补齐 CI / SDV / CodeQL。

架构概览

项目为单驱动设计，五个二进制组件：

AgentLensKernel.sys

合并控制设备、minifilter、WFP callout 与 6 类监控回调（进程 / 线程 / 镜像 / 注册表 / 对象句柄 / 网络），事件写入 1 MiB 共享环形缓冲并同步发 ETW。

AgentLensService.exe

系统服务。从共享环或 IOCTL 读取事件，输出 JSON Lines（含 DNS 名称关联），并运行 AgentLensAgent 的命名管道服务器。

AgentLensAgent.dll

注入目标进程。上报工作目录、环境变量计数、镜像 SHA-256、签名状态与调用栈摘要。

AgentLensTools.exe

控制 / 诊断 CLI：版本、统计、订阅、策略装载（文本策略编译器）、自测、fuzz、驱动启停。

AgentLensEtw.exe

独立实时 ETW 消费者，用于验证内核 ETW 输出与 DNS 关联。

数据流：内核回调 → AglEventEmit → （环形缓冲 → 共享内存 / IOCTL 读取）与（ETW 会话）→ 服务输出 JSON Lines。控制流：Tools / Service / Agent 通过 \\\\.\\AgentLensControl 的单 IOCTL 通道（表驱动分发，12 个操作码）执行订阅、读事件、装载策略、更新上下文等。

严重问题（S1–S5）

S1 严重服务以只读映射写共享环 Tail，第一批事件即访问违规

src\AgentLensService\event_reader.cpp:112,118,183

OpenSharedRing 用 OpenFileMappingW(FILE_MAP_READ) 与 MapViewOfFile(FILE_MAP_READ) 映射节，但 ReadShared 读取到数据后执行 m_header->Tail = …。对只读视图写内存会触发 STATUS_ACCESS_VIOLATION。

影响只要魔数校验通过（内核在运行时成立），ReadOnce 就永远优先走共享环路径；一旦有事件到达即崩溃，IOCTL 回退永远不会发生。服务主路径当前不可用。
建议短修：以 FILE_MAP_READ|FILE_MAP_WRITE 映射。长修：与 S2/S3 一起重设计消费协议——由内核独占推进 Tail（消费者只读），或干脆让服务统一走 IOCTL 读取。
S2 严重双 Tail 账本分裂：内核空闲空间永不回收，最终全量丢事件

src\AgentLensService\event_reader.cpp:183 与 src\AgentLensKernel\agl_event_ring.c:194-204

内核写侧用内部变量 AglEventRing.Tail 计算 used/freeSpace；用户态只更新共享头的 Tail，内核内部 Tail 仅在 IOCTL 读取路径（agl_event_ring.c:296）前进。共享模式读得越多，内核看到的“已用空间”越大。

影响环形缓冲被内核认为“写满”后，所有后续事件（含 CRITICAL 事件）全部被丢弃，CriticalDropped 持续增长；即使消费者已经把数据读空。这是事件通道的静默失效。
建议单一事实源。推荐方案 A：消费者完全通过 IOCTL 读取（内核是唯一推进 Tail 的一方），共享映射仅用于只读统计快照；方案 B（内核信任用户写回的共享 Tail）不推荐，违反内核安全产品不该信任用户态的原则。
S3 严重环形缓冲溢出不保帧边界；IOCTL 读取切分记录后无法恢复

src\AgentLensKernel\agl_event_ring.c:204-226（写侧）、281-296（读侧）

写侧只对“CRITICAL 且空间不足”做丢弃，非关键记录在空间不足时直接覆盖未读区域，Head 越过 Tail，被覆盖记录的前半部分变成垃圾 RecordLength。读侧按字节数切分（最多 BufferLength 字节），一条记录可能被拆到两次读取中，客户端 PrintJsonEvents 没有 carry-over 缓冲，遇到不完整记录即 break，剩余字节全部静默丢弃。

影响流量高峰下记录流损坏：单条损坏即导致后续若干事件被解析器丢弃；溢出覆盖不增加 Dropped 计数，运维无法察觉。S1/S2 修复后此问题会立刻暴露。
建议写侧：空间不足时按整帧跳过未读记录（推进到下一记录边界）并 Dropped++，可选写入恢复标记帧。读侧：只按完整记录推进 Tail，或客户端维护跨次读取的 carry-over 缓冲。同时给解析器加“重同步”逻辑。
S4 严重策略 epoch 回收存在 read-then-increment 竞态，潜在 use-after-free

src\AgentLensKernel\agl_policy.c:117-126（读者进入）、145-166（发布与等待）

AglPolicyReaderEnter 先读当前 epoch，再对 readers[epoch] 自增，两步之间没有原子性：若写线程恰在窗口内发布新快照并完成对旧 epoch 的等待（读者尚未登记，计数为 0），随后读者登记的是旧 epoch、使用的却是下一个快照。连续两次热更新（A→B→C）时，第二次回收等待的是 readers[1]，而读者登记在 readers[0]，B 可能被提前释放，读者继续解引用 → UAF。

影响内核模式 use-after-free，触发条件为策略热更新与监控回调并发，属于低频但高危的正确性问题；安全产品中不可接受。
建议标准修正：读 epoch → 自增计数 → 内存屏障 → 重读 epoch，若变化则回退计数并重试；或在读取快照指针后再登记。写侧继续等待 retiredEpoch（现有 spinlock 已序列化发布）。
S5 严重自旋锁内分配 / 释放分页池，IRQL 契约违规

src\AgentLensKernel\agl_context.c:228-281（分配）、27-33 与 82-101（释放）

AglContextGetOrCreateProcess 持 KSPIN_LOCK（IRQL 被提升到 DISPATCH_LEVEL）期间调用 AglCopyUnicodeString(PagedPool) 分配分页内存；AglContextDestroy 同样持锁释放 PagedPool 分配的 ImagePath/ImageName/CommandLine 缓冲。DISPATCH_LEVEL 下触碰分页池违反 IRQL 契约，一旦相关页面被换出即 IRQL_NOT_LESS_OR_EQUAL 蓝屏。进程创建回调本身虽在 PASSIVE，但代码先拿了自旋锁。

影响进程创建 / 驱动卸载路径的潜在蓝屏；低内存压力下触发概率上升。
建议路径字符串一律 NonPagedPool（当前上下文数据本身存于非分页结构，语义上也应如此）；或改“锁外分配、回锁校验、重复则释放”。Destroy 收集节点后在锁外统一释放。

高优先级问题（H1–H8）

H1卸载路径漏掉 ETW provider 反注册

src\AgentLensKernel\driver.c:124-188

DriverEntry 调用了 AglEtwInitialize（driver.c:37），失败回滚路径也调用了 AglEtwUninitialize（driver.c:118），但 AglDriverUnload 中完全没有反注册。每次卸载 / 重载泄漏一个 EtwRegister 的 provider 注册。

影响tests\stress_reload.cmd 的 100 次重载循环会放大为 100 份泄漏；长期反复加载驱动（开发 / 调试常见）导致内核资源累积。
建议在 AglDriverUnload 末尾补一行 AglEtwUninitialize()。
H2注册表 key 上下文只在删除 key 时清理

src\AgentLensKernel\agl_registry_monitor.c:41-67（入链并持引用）、419-426（post-open 加引用）、537-543（仅 PreDeleteKey 移除）

每次成功的 key 创建 / 打开都向全局链表插入一个持 ObReferenceObject 引用的上下文；移除只发生在 RegNtPreDeleteKey。未处理 RegNtPreKeyHandleClose / RegNtPostKeyHandleClose / RegNtCallbackObjectContextCleanup，被打开但从不删除的 key 永久驻留。

影响非分页内存与 key 对象无界增长（进程枚举大量 key 即可放大）；持有引用还会延迟 key 对象销毁、可能阻碍 hive 卸载。这是一个可被恶意利用的资源耗尽面。
建议用 handle-close / callback-context-cleanup 通知移除上下文。注意 MSDN《Invalid Key Object Pointers in Registry Notifications》：close 类通知中的 Object 指针状态无效，不能对之调用 ObReferenceObjectByPointer，应使用 CmRegisterCallbackEx 的 ObjectContext 机制或按值匹配。
H3服务端解析信任未校验长度，损坏 / 伪造记录可致越界读

src\AgentLensService\event_reader.cpp:264-329

JSON 解析路径只校验 header->StructSize，没有校验 PayloadLength 不超过记录剩余字节，随后按 file->PathLength / reg->PathLength / domain->SniLength 读取 Data。这些长度字段来自环内数据；共享 section 是 PAGE_READWRITE 且未显式设置 DACL，若低权限进程可获得映射写访问，就能向 SYSTEM 权限的服务注入伪造记录。

影响越界读取（视图范围内，可能泄出相邻记录内容并随 JSON 输出）或服务崩溃；最坏情形构成对特权服务的攻击面。
建议解析前完整校验：PayloadLength ≤ RecordLength - 环头 - 事件头；各固定字段长度与 Data 长度之和 ≤ PayloadLength。给 section / 事件命名对象显式 DACL（SYSTEM + Administrators，必要时服务 SID），消费者只映射读。
H4网络事件负载内嵌冗余零化事件头

src\AgentLensKernel\agl_network_monitor.c:338-347、443-459

AglNetworkClassify 与 AglNetworkFlowDelete 调用 AglEventEmit 时把整个 AGL_NETWORK_EVENT（含一个零化的 AGL_EVENT_HEADER）作为 payload；而 token 事件（agl_event.c:235-243）明确跳过头部只传字段。两个消费端（event_reader.cpp:342-346 与 AgentLensEtw main.cpp）都必须“偏移一个头”补偿，这是靠巧合对齐的隐式协议。

影响负载布局不一致、易错；未来统一 payload 规则或重构事件发射会静默破坏网络事件的解析。
建议统一为“payload 不含头”，网络事件传 &event + sizeof(AGL_EVENT_HEADER) 之后的字段，与 token 事件一致；同步修正消费端。
H5文件读 / 写事件 90% 静默采样丢弃

src\AgentLensKernel\agl_event.c:9-15、59

AglShouldSampleEvent 对 FILE_READ / FILE_WRITE 每 10 个只保留 1 个，丢弃行为在 README 中没有任何说明，也没有在统计里体现采样数。

影响文件活动是 EDR 类产品的核心取证数据，静默采样会造成可被利用的观察缺口，且使用者无感知。
建议至少文档化；更优：采样率可配置（策略 / IOCTL），并在 AGL_STATS 中暴露采样丢弃计数。
H6ETW manifest 与实现不一致

src\AgentLensKernel\agl_etw.c:11-12 / etw\AgentLensProvider.man:13-26

驱动写的是 EVENT_DESCRIPTOR id 1000，manifest 却只声明了 1001–1005；且 manifest 事件没有 template（无 payload 定义）、缺 task / opcode、channel 默认 enabled=false。wevtutil 导入后按 manifest 无法解码驱动实际发出的事件。

影响ETW 侧只有原始字节可读（AgentLensEtw 自己按结构解析），第三方日志 / SIEM 集成无从下手。
建议对齐事件号，补齐 template 与用户数据布局；若产品定位就是原始事件流，则删除误导性 manifest 或在文档中明确。
H7样例策略使用引擎不支持的通配符

config\sample.policy:5-14 / src\AgentLensKernel\agl_policy.c:545-560

样例写 path = C:\Users\*\Desktop\*，但 AglMatchString 只做大小写不敏感的前缀匹配（RtlPrefixUnicodeString），* 被当作普通字符；process = agent.exe 与完整镜像路径做前缀匹配也永远不会命中。这意味着样例策略实际上一条都不会触发 deny。

影响用户照着样例配置得到“策略不生效”的结果，安全产品的策略语义误导风险高。
建议二选一：实现通配符 / glob 匹配（注意内核实现要受控）；或明确文档化“前缀匹配”语义并修正样例（写完整路径前缀）。文本策略编译器应对不支持的语法给出告警。
H8安全编译基线不足

各 vcxproj；内核项目 SpectreMitigation=false 共 5 处（AgentLensKernel.vcxproj:19,26,32,39,45）

全部项目：Spectre 缓解关闭；TreatWarningAsError=false；未启用 /sdl（SDL 检查）；无 CI、无 SDV、无 CodeQL（README 已自行承认）。

影响针对内核的侧信道 / 整型溢出类编译器级缓解缺失；警告无法拦截回归。
建议内核开启 /Qspectre、/WX、/sdl；用户态组件同样建议开启；接入 CI + SDV + CodeQL（微软有公开的驱动 CI 模板）。

中优先级问题（M1–M10）

M1进程退出事件丢失关联信息

src\AgentLensKernel\agl_process_monitor.c:197-210

退出分支先调用 AglContextRemoveProcess 再发 PROCESS_EXIT 事件，此时 CorrelationId / AgentSessionId 已查不到，事件头里的关联字段退化为序列号。

建议先取上下文快照（关联 ID、会话 ID）再移除，或由 RemoveProcess 返回快照。
M2服务 STOP 处理不完整

src\AgentLensService\service.cpp:48-60

收到 SERVICE_CONTROL_STOP/SHUTDOWN 仅把状态置为 STOPPED，不设置退出信号、不停止读取线程 / DNS 会话 / 管道服务器，依赖 SCM 强杀进程。

建议使用事件对象协调各线程退出、反订阅、停 ETW 会话后再置 STOPPED。
M3共享 section / 事件命名对象无显式安全描述符

src\AgentLensKernel\agl_event_ring.c:20-22、91-106

InitializeObjectAttributes 传入 NULL 安全描述符，对象安全取决于默认 DACL。共享节允许写（PAGE_READWRITE），一旦非管理员可获写访问，H3 的可利用性大幅上升。

建议显式 SDDL（SYSTEM+BA），消费者只读；在测试 VM 上用低权限账户验证 open 失败。
M4订阅计数与句柄生命周期脱钩

src\AgentLensKernel\agl_event_ring.c（ActiveSubscribers 全局计数）

订阅是全局计数而非 per-handle 状态：客户端未 unsubscribe 就关句柄时计数不回落；多客户端时无法按订阅者路由。

建议改为文件对象（FsContext）维度跟踪订阅状态，清理回调时自动退订。
M5pre-create 直接解引用 SecurityContext

src\AgentLensKernel\agl_file_monitor.c:156、266

Parameters.Create.SecurityContext 在少数重解析 / 特殊来源的 create 中可能为 NULL，无条件解引用是潜在空指针。增加防御性检查成本极低。

M6cwd.MaximumLength 可能回绕

src\AgentLensKernel\agl_control.c:359

CurrentDirectoryLength=65535 时 MaximumLength=Length+2 回绕为 1；后续字符串操作依赖错误的 MaximumLength。输入虽限 2048 字节，但该上限应同时用于 MaximumLength 计算。

M7策略快照内存放大

src\AgentLensKernel\agl_policy.c:19-36

每条规则内联 3×1024 宽字符缓冲（≈6 KiB），128 条规则约 786 KiB 非分页内存 / 快照，发布切换期间双份。可接受但应评估上限与改用指针式存储。

M8Agent 上报 JSON 未转义

src\AgentLensAgent\dllmain.cpp:267-272

image / command / cwd 直接拼进 JSON，路径含反斜杠或引号时 JSON 无效（Windows 路径必含反斜杠）。服务端仅原样打印，暂不影响流程但格式已不合法。

M9服务侧死代码

src\AgentLensService\policy_loader.cpp、config.cpp

LoadPolicyFile 与 LoadConfig 未被任何调用点使用，属于未接线脚手架。

M10安装路径双轨且 INF 不完整

config\AgentLensKernel.inf / installer\install.cmd

INF 的 DefaultInstall 使用 CopyFiles 但缺少 SourceDisksNames / SourceDisksFiles 段，标准安装方式无法定位源文件；实际安装走 install.cmd 手工 sc create，两套路径易漂移。DriverVer 日期 07/01/2026 已过期。

做得好的地方

架构与分层。协议头（include\AgentLensProtocol）与内核 / 用户态实现边界清晰；DriverEntry 与 Unload 的初始化 / 回滚严格成对（仅缺 ETW 反注册），失败路径回滚顺序正确。

上下文管理。引用计数 + tombstone 延迟回收 + PID 与创建时间双重校验，规避 PID 复用误匹配，是成熟的内核上下文做法。

事件模型。版本化 schema、全局序列号、关联 ID、Agent 会话 / 对话 / 工具调用标记、CRITICAL 标志，支撑跨组件关联分析。
网络观测。WFP ALE 全层覆盖（connect / recv / flow / close / stream）、流层字节与包统计、尽力 TLS SNI 提取、DNS Client ETW 关联——功能完整性在同类原型中相当好。
工程配套。自带 selftest、结构化 IOCTL / 策略 fuzz、Driver Verifier、压力重载脚本与结果模板，验证意识好。
